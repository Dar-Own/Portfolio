# Period-start checkpoint replacement suppresses a valid coverage payout

## Description

An exiting staker can make the period-start asset checkpoint exclude collateral that remains physically held during its withdrawal delay. Incident payout later caps exposure using the modified historical value. The original submitted sequence uses an ERC-721 receiver callback after commitment; a later funded first-loss-buffer scenario uses an ordinary withdrawal before a later honest commitment. These are one checkpoint root cause.

The original callback case requires honest commitment and first settlement at exact start(P). The stronger funded-buffer variant only needs the withdrawal at that boundary; it still depends on a legitimate covered incident and honest assessment. A +1-second control pays the missing vault leg. The later scenario came from an externally supplied comparison package and is supporting evidence, not a second individually discovered finding. No accepted organizer severity or current deployment/remediation is inferred.

### Mechanism step by step

#### Step 1 — Reduce active exposure immediately on withdrawal

Withdrawal reserves a delayed claim but logs assets minus the requested amount immediately.

Source: `contracts/core/[project]Vault.sol:771-777`

```solidity

        uint256 ownerBalance = _requestWithdraw(assets, shares, receiver, owner);
```

#### Step 2 — Write the checkpoint at the current timestamp

At exact period start, the new checkpoint shares the key used by the period exposure query.

Source: `contracts/core/[project]Vault.sol:1044-1056`

```solidity
    function _logTrace(
        address owner,
        uint256 balance,
        uint256 _totalSupply,
        uint256 _totalAssets,
        bool isLogAssets
    ) private {
        uint48 ts = Time.timestamp();
        _traceBalanceOf[owner].push(ts, balance);
        _traceTotalSupply.push(ts, _totalSupply);

        if (isLogAssets) _traceTotalAssets.push(ts, _totalAssets);
    }
```

#### Step 3 — Replace an existing same-key value

A checkpoint with the same key overwrites the final stored value. Historical lookup therefore does not freeze the earlier period-start exposure.

Source: `contracts/core/lib/Checkpoints.sol:198-213`

```solidity
    function push(Trace256 storage self, uint48 key, uint256 value) internal returns (uint256, uint256) {
        if (self._values.length == 0) {
            self._values.push(0);
        }

        (bool exists, uint48 lastKey,) = self._trace.latestCheckpoint();

        uint256 len = self._values.length;
        uint256 lastValue = latest(self);
        if (exists && key == lastKey) {
            self._values[len - 1] = value;
        } else {
            self._trace.push(key, uint208(len));
            self._values.push(value);
        }

```

#### Step 4 — Cap incident payment with the lowered historical value

Even with enough physically held delayed-withdrawal assets, the minimum with assetsAtCapturePeriod can force zero payment.

Source: `contracts/core/[project]Vault.sol:911-927`

```solidity
        uint256 assetsAtCapturePeriod = totalAssetsAt(capturePeriodStart);
        uint256 currentActiveAssets = totalAssets();

        // Withdrawals requested during the capture period are assigned to capturePeriod + 1
        // and remain payable while payout is allowed.
        uint256 capturePeriodWithdrawals = withdrawAssets[capturePeriod + 1];

        // If payout happens in the following period, withdrawals requested before payout
        // during that following period are assigned to capturePeriod + 2 and should also
        // remain payable; otherwise exposed assets could escape by withdrawing first.
        uint256 nextPeriodWithdrawals;
        if (_currentPeriod == capturePeriod + 1) {
            nextPeriodWithdrawals = withdrawAssets[capturePeriod + 2];
        }

        uint256 activePayableAmount = currentActiveAssets + capturePeriodWithdrawals + nextPeriodWithdrawals;
        paidAmount = Math.min(amount, Math.min(assetsAtCapturePeriod, activePayableAmount));
```

## Proof of concept

The local Hardhat fixture deploys vault, allocator and incident contracts, mints collateral, funds the first-loss buffer and performs the required authorized actions. The boundary-withdrawal case and periodStart+1 control differ in timing. Historical results record a 200 valid loss, 100 buffer payment and zero of the remaining 100 vault leg; the staker receives 1,000 collateral instead of the control’s 900. The original unfunded-buffer scenario is the same root cause, not another finding. Payments to the aggregate receiver are measured; subsequent beneficiary distribution is not.

**Proof limits:** Constructed incident and timing; aggregate receiver accounting, not final off-chain distribution.
